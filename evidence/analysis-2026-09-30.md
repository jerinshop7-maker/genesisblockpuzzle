Block 968981 asked, in one letter each:

> 1) jq/cut/tr changed: a) the text before sha256sum b) only sha256sum's output
>    (e.g. cut -c1-32). 2) Words: a) Coleman "12 words" on that text
>    b) first 32 hex as raw entropy

Block 968996 answered:

> 1) a; 2) b.

So the pipeline is:

```
bitcoin-cli / explorer output  ->  cut|jq|tr (edit the text)  ->  sha256sum
                                                                      |
                                       first 32 hex chars  <---------+
                                              |
                                       12 BIP39 words  ->  passphrase  ->  keys
```

Note what this **closes**: the earlier suggestion (block 967477) that the digest
input might be viewed as binary, hex, decimal, or ASCII is no longer the primary
axis. The author says the input is a contiguous piece of the block *as printed by
a tool*, then transformed. The tool chain is named: `bitcoin-cli`, `cut`, `jq`,
`tr`, `sha256sum`.

## What `bitcoin-cli getblock <hash> 0` actually prints

This matters because the author said he copy-pasted the tool's output verbatim.
`bitcoin-cli getblock <genesis-hash> 0` emits the serialized 285-byte block as a
single **570-character lowercase hex string**, one line, no wrapping. Explorers
such as mempool.space render the identical 570 hex characters, usually wrapped
across lines.

So the realistic digest-input space is:

| Source | Contiguous ranges |
|---|---:|
| 570-char hex of the whole block | 570·571/2 = **162,735** |
| 285 raw bytes | 285·286/2 = 40,755 |
| 69-byte Times text | 2,415 |
| 47-byte headline | 1,128 |

with the `cut`/`tr` step already accounted for by the fact that we simply try
*every* contiguous range rather than guessing the author's exact command.

This is a large reduction in the digest axis: we no longer need to enumerate
representations of every field, only contiguous ranges of the tool-printed forms.

## Open axes that remain

1. **Which contiguous range.** Brute-forceable now: 162,735 candidates for the
   full-block hex. This is the axis the author explicitly said to brute force
   ("Genesis block is extremely small. This will have to be uncovered via
   brute-force", block 968768).
2. **The passphrase.** Confirmed to be "a name". The format is deliberately left
   for brute force (block 967383: "You'll have to discover the fmt through brute
   force. The key question greatly narrows the search space."). "The key
   question" is the question at 967106, "Do both cosigners use the same 12 words
   and the same passphrase?", which the author never answered directly. The
   standing hypothesis is **Hal Finney** (recipient of the first Bitcoin
   transaction), with Satoshi Nakamoto as the secondary candidate.
3. **The BIP48 account number.** `genesis_data` is "some data from the genesis
   block used as the BIP48 account number". Candidates: nonce (2083236893),
   time (1231006505), bits (486604799), the year 2009, a date integer, or a
   4-byte window of some field reduced below 2^31.
4. **The two leaf paths.** Both keys sit under `m/48'/0'/ACCOUNT'/2'`. The
   questioner at 968603 reads the origins as
   `[fingerprint/48h/0h/acct'/2h]`, i.e. depth 4 with the two keys distinguished
   below that. Standard candidates are the external-chain pair `0/0` and `0/1`,
   and the cosigner-branch pair `0/0` and `1/0`.

## Why the two keys are probably NOT two leaves of one seed

The author said both keys "use the same Genesis field" and are "derived
independently from Genesis". A plain 2-of-2 multisig wallet has two *different*
seeds, one per cosigner, and both are used at the *same* path
`m/48'/0'/ACCOUNT'/2'/<x>/<y>`. Since the author also says the passphrase is a
singular "a name", the most economical reading is:

- one 12-word seed and one passphrase,
- but two independent BIP32 roots, because the two cosigners each ran the
  derivation on their own machine, or
- two leaves under one root.

Both are enumerated. The independent-root model is the one the Sept 25 notes
flagged as untested, and it is cheap to add now that the engine caches nodes.

## The number that actually matters

At block 968713 the author wrote:

> The genesis block is only 2.5E-32 of the 2^128 possibilities.

This is the author's own estimate of how small the entropy space is, and it is
consistent with "the digest input is one specific contiguous range of a known
285-byte block", i.e. a search space of order 10^5, not 2^128. It also explains
why the author refused to reveal the seed's master fingerprint even for 30k:
with the fingerprint and the account number, the remaining unknown would be only
the passphrase format.

## Status of the sweep

`solve.py` + `engine.c` are running the digest x passphrase x account x leaf-pair
matrix. Both are cross-validated against the pinned reference (see
`verification-2026-09-30.md`). No match has been found yet. Any claim of a
solution requires an exact SHA-256 match on the witness script, and nothing
weaker will be reported.
