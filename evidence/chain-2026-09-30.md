## What this settles

Reading the block 968981 question against the block 968996 answer:

- **1) a** — `jq`/`cut`/`tr` modified **the Genesis text before it was hashed**,
  i.e. the pipeline is `cut/jq/tr <genesis text> | sha256sum`, and the
  transformation happens upstream of the digest, not on the digest output.
- **2) b** — the 12 words come from **the first 32 hex characters of the
  sha256sum output used as raw entropy**, which is exactly
  `SHA256(digest_input)[0:16]` as confirmed at block 968343. This corroborates
  the earlier confirmation rather than replacing it.

Combining with block 968601 ("a contiguous piece ... copy-pasting the tool's
output") the digest input is now pinned to:

> a contiguous byte range of the Genesis block, in the exact textual form a
> standard tool prints, optionally transformed by `cut`/`jq`/`tr` before hashing.

This is a large reduction. It removes the decimal/ASCII/bitstring representation
matrix from block 967477 as the primary axis: the input is a *tool-printed*
contiguous range, not an arbitrary re-encoding. The remaining search is over

## Important correction to the prior notes

The prior handoff's "Promising discovery" and all negative results produced by
`evidence/search_bip48.py` are **not trustworthy**. That script defines

```python
N = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141
```

and uses that single value for BOTH the secp256k1 field modulus (point
arithmetic) and the group order (BIP32 child addition). Only the group-order use
is correct. Point arithmetic modulo the group order is wrong, so every derived
public key from that script is wrong. Every "no match" it reported is therefore
meaningless, and the interrupted sweeps described in the Sept 23/25 logs should
be treated as untested rather than negative.

The replacement engine in `evidence/engine.c` uses the correct split and is
pinned to ground truth (see `evidence/reference.py`).
